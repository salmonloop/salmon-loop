## YYYY-MM-DD - Batched Concurrent Operations for Artifact GC
**Learning:** Optimization of operations that iterate over large numbers of files (e.g. `ArtifactStore.gc`) using batched concurrent `fs.stat` and `fs.rm` checks (e.g. `Promise.all` with chunk sizes of 10) prevents severe performance bottlenecks and EMFILE limits. When optimizing file operations that depend on dynamically updated cumulative totals (e.g., calculating `removedBytes` against a `maxTotalBytes` limit), we must first evaluate the files sequentially to build a safe removal queue. Only after the queue is built should the actual file deletions (e.g., `fs.rm`) be executed concurrently in chunks to prevent race conditions during state calculation.
**Action:** Use chunked sequential queue evaluation and parallel deletion pattern for file management operations in the codebase.
